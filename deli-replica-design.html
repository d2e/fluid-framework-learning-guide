R = P (8 Pods, 8 Parts) 1:1 Dedicated

Each container sequences exactly 1 partition. Dedicated CPU core isolation, no contention between active documents on different partitions.

R < P (4 Pods, 8 Parts) 1:Many Multi-Tenancy

Each pod instantiates multiple Partition objects in PartitionManager. Concurrency is shared within the Node.js event loop.

R > P (12 Pods, 8 Parts) Idle Warm Standbys

Kafka assigns 0 partitions to the extra 4 pods. They sit idle as warm standbys ready to instantly claim partitions during node failure or rolling upgrade.

State Durability & Failover Invariants
Layer Role Guarantee
Kafka rawdeltas Input buffer Immutable unsequenced log. Replay source on crash.
Deli Container Sequencer Strict monotonic counter. concurrency=1 per partition.
Kafka deltas Output broadcast Total Order Broadcast (ToB) for all clients and Scriptorium.
MongoDB Durable checkpoint Stores latest sequenceNumber and client roster.
Why Deli Containers Don't Need Disks

Because checkpoints live in MongoDB and the uncommitted delta log lives in Kafka, Deli pods are completely ephemeral. A pod can be killed with SIGKILL without losing a single sequence number or corrupting document state.

3 Failover Lifecycle: When a Container Replica Dies
T0 — Normal Operations
Replica 2 runs Partition 1 (Active)
Ops stream from rawdeltas into Pod 2. Monotonic sequence counter advances: #500 → #501 → #502. Checkpoints periodically saved to MongoDB.
T1 — Crash / Hardware Failure
Replica 2 Terminated (OOM / Pod Eviction)
Heartbeat signal to Kafka ceases. Kafka Broker starts timer session.timeout.ms (default 10s or 45s).
T2 — Cooperative Rebalance
Kafka Group Coordinator Rebalances
Kafka triggers consumer.on("rebalancing"). Surviving pods drain in-flight ops. Kafka’s cooperative-sticky assignor assigns orphaned Partition 1 to surviving Replica 1.
T3 — Hydration & Replay
Replica 1 Reconstructs State
Replica 1 invokes new Partition(1) → reads checkpoint from MongoDB (`sequenceNumber: 502`) → seeks Kafka consumer to offset 503 → replays rawdeltas.
T4 — Full Recovery
Sequencing Resumes With Monotonic Guarantees
Subsequent op gets sequenced as #503. Total recovery time < a few seconds. Zero split-brain because Kafka enforces 1 consumer per partition.
